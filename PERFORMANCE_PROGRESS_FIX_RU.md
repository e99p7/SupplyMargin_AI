# Исправления производительности и прогресса расчётов

## Что изменено

- Прогноз спроса рассчитывается пакетами по нескольким SKU, вместо отдельного вызова `model.predict()` и создания DataFrame для каждого SKU на каждом шаге горизонта.
- Построение признака `rolling_3` переведено на векторизованный `groupby/rolling`, без Python-lambda на каждую группу SKU.
- Перебор ценовых кандидатов выполняется пакетно через NumPy; сохранены 61 кандидат, число симуляций и детерминированные потоки случайных чисел для каждого кандидата.
- Исправлена проверка минимального количества обучающих периодов: используется `table`, а не несуществующая `train_df`.
- Backend сохраняет этап, сообщение и процент расчёта в `Run.summary_json`; отдельная миграция базы не требуется.
- API `/v1/runs` возвращает поле `progress`, а интерфейс показывает полосу выполнения и текущий этап.

## Проверки

- `python -m compileall -q supplymargin` — успешно.
- `pytest -q tests/test_pipeline.py tests/test_data.py tests/test_integration.py tests/test_shadow.py` — 7 тестов прошли.
- Проверка пакетного прогноза на синтетической истории со 100 SKU и горизонтом 14 периодов показала ускорение примерно в 28 раз относительно прежнего цикла с отдельным вызовом модели на каждый SKU/период. Это микробенчмарк; фактическое время полного расчёта зависит от объёма данных и окружения.
- Результаты векторизованного перебора цен совпали с прежним расчётом в пределах погрешности float64 (максимальная абсолютная разница около 7.3e-12 в контрольном примере; лучший кандидат по цене совпал).

## Ограничения

Цель «до 1 часа» нельзя гарантировать без измерения на реальном production-наборе и сервере. Рекомендуется сравнить время и метрики качества (WAPE/MAE), а также итоговые рекомендации на контрольной выборке до и после внедрения.
